# Trusted cannon alignment (Campus 0.9.0 / feeder 1.4.0)

## Automatic location and setup

Feeder 1.4.0 reports its numeric ComputerCraft ID and the currently detected inventory side, including before the first blueprint assignment. Campus reads the saved overworld inside its configured campus area and finds that exact computer. Its facing and local side determine the selected adjacent inventory. Exactly one face-adjacent Schematicannon must be present. Duplicate computer IDs, ambiguous cannon neighbors, remote peripherals, double chests and unsupported inventory types are refused with an explanation. A newly placed or moved computer may take until Minecraft next saves the world to appear.

The signed host `discover` action verifies the candidate against live blocks before storing the physical binding. It checks computer identity and facing, inventory and cannon adjacency, and other registry assignments. An unchanged binding preserves the current schematic, receipt and native state. A changed binding requires safe old/new cannon states; no discovery action starts, resets or replaces a native printer.

Newly discovered stations default to automatic rest-plan preparation. Explicitly configured schematic settings, including `enabled:false`, remain unchanged. Select a blueprint in the web app to generate and insert the rest schematic with that version's target and cannon settings. Existing active jobs wait for a safe stop. Only the explicit Start/Resume action starts construction.

Automatic discovery runs periodically and can be retried with `POST /api/cannons/:name/discover` by a browser-session admin. Its status appears under `alignment.discovery`. Discovery failures block automatic operation; missing coordinates are never guessed. Set `CANNON_DISCOVERY_ENABLED=false` to disable the automatic workflow. New automatic bindings use `CANNON_SCHEMATIC_OWNER` (default `Campus`); an existing binding retains its upload owner.

Manual probe/bind remains available as an advanced fallback. It requires a fresh supported feeder and explicit confirmation of a short-lived probe nonce. The legacy full-NBT apply route requires the exact version uploaded through Create's Schematic Table; automatic preparation creates and inserts its own managed item directly.

Bound station deletion/recreation is rejected to prevent accidental removal of the supply gate. Bound assignments/options require browser-admin authorization. Material permission requires the exact selected revision, a matching receipt and a fresh native observation. Failed identity, options, hash, position or printer checks leave the feeder paused without material, gunpowder or crafting permission. Feeder leases expire after ten seconds.

## Automatic rest-plan preparation

The legacy full-NBT alignment workflow above remains available. Automatically discovered stations enable **Schematic automatisch vorbereiten** unless settings were already explicitly configured; manual bindings can enable it in settings. That explicitly authorizes the signed `/campus/prepare` action to upload an immutable rest file below the confirmed owner and write a deployed Schematic into the cannon's input, including bounds, origin, no rotation/mirror and chosen cannon options. Preparation only supports the overworld snapshot. The rest file has its own UUID filename and SHA256, so legacy full-version hashes are never confused with it. New plan versions are staged automatically; a changed snapshot alone does not create a new job. Explicit refresh uses the newest existing snapshot.

The controller requires STOPPED, zero placement counters, an empty initialized-state printer and no in-flight blocks. It refuses foreign/manual Schematics. It preserves all non-input slots, consuming one existing empty output Schematic when available; otherwise it reuses its own managed input or creates the initial managed item. Numeric types in preserved item components remain intact. A backup of the old block SNBT is stored in `discord/campus-schematic-backups`. Short RCON commands stage inventory and options in temporary command storage, removed after each attempt. A single guarded root merge then checks the observed inventory, empty slots, state, counters, block type and absence of printer cache before merging inventory/options. Preparation never starts or resets a cannon. Starting is a separate browser-admin action described below. Live readback must match item components, hash and options. The app then records the receipt and advances the feeder assignment/version together. Options drift blocks subsequent material leases.

The host route requires the existing HMAC and registry. Browser admins alone configure or explicitly refresh preparation. Station and ordinary write tokens cannot configure it or upload a Schematic. Each RCON command is limited to 950 UTF-8 bytes to stay below the native packet limit; unusually large book/item metadata is refused with a request to remove those items first. The RCON client also has an in-container timeout so failed guards cannot leave orphaned clients. Its bounded body limit is 24 MiB, with compressed NBT limited to 16 MiB. No additional token or background host worker is installed.

## Boundary and races — not an immutable build lock

This is a **Campus feeder interlock**, not an in-server Create mod or a native GUI lock. Players can still start Create through its GUI and supply materials manually. Materials already in a chest, fuel already loaded, in-flight blocks and cached CC permission within its short lease cannot be recalled. Do not use this as a real-time world protection mechanism.

Do not operate the native GUI during apply. The final write is a single server-thread `execute if block ...` command, rechecking canonical block identity, STOPPED state, zero counters, input filename/owner and absence of cached `Printer.Anchor`/`CurrentPos` at the write instant. Legacy alignment apply merges **only four components** (anchor int array, rotation, mirror, deployed) on integer input `Slot:0`, preserving all other item components, inventory slots, cannon NBT and fuel. It neither replaces the whole inventory nor changes counters/state. Readback must confirm the stopped zero-counter target and exact components/hash; no rollback is attempted against a potentially newly active printer. RCON sequencing and readback do not establish a permanent GUI/player lock. The serialized printer exposes its anchor but not a separate cached rotation/hash; live checks include item components, file hash and the printer anchor, backed by the prior guarded apply receipt. Native edits remain outside the enforcement boundary.

## Host integration

`controller/campus_cannon.py` is stdlib-only. Install beside the existing host `control.py`; `controller/control.patch` is the small integration patch. The runtime remains `/home/logge/minecraft/atm10/discord/control.py` under `atm10-control.service`. The preparation extension also requires `campus_discovery.py`, `campus_schematic.py`, `campus_snbt.py`, `campus_probe.py` and `campus_start.py` beside `control.py`. Only this service needs restart, **not Minecraft**. Existing Discord `/status`, `/events`, `/action`, `/chat`, `/awake` routes and credentials are unchanged.

The controller binds to its existing internal `172.17.0.1:25576`. A separate random mode-0600 `discord/control/campus-secret` authenticates the POST routes: `/campus/discover`, `/campus/probe`, `/campus/bind`, `/campus/inspect`, `/campus/apply`, `/campus/prepare`, `/campus/start`. Requests are HMAC-SHA256 signed over path, timestamp, unique nonce and exact body, expire after 30 seconds, reject replay and any browser Origin, and have bounded body size. The old Discord bearer token does not authorize these routes; the Campus signing secret does not authorize server stop/restart/chat. The secret is host/server-only (`CANNON_BRIDGE_SECRET`), never returned to browsers or CC. Set `CANNON_BRIDGE_URL=http://172.17.0.1:25576` and persist both environment variables in Dokploy's application configuration.

The host registry is `discord/cannon-registry.json`, created by confirmed manual binding or live-verified automatic discovery. Inspect/apply take only an existing station name; candidate probe accepts strictly validated dimension/coordinates/owner and is read-only. Supported dimensions are overworld, Nether, End; x/z within world bounds, y -64..319, vanilla-safe owner, canonical uploaded filename and hash. Uploaded files are read only below `data/schematics/uploaded/<owner>/`; symlinks/traversal are refused. There is no arbitrary command/RCON endpoint, Docker socket in Campus, world-file write path, inventory overwrite, mod install, Discord post, or Minecraft restart.

The installed Create 6.0.10 jar was inspected: STOPPED resets a loaded printer in `tickPrinter`; the serialized uninitialized `Printer` contains `DeferredBlocks:[]`, `PrintStage:"BLOCKS"`, `EntityProgress:-1` but no `Anchor`/`CurrentPos`. Input inventory Slot is an **int**, not a byte. Anchors use `[I;x,y,z]`. `rcon-cli` appends ANSI reset sequences, stripped before bounded fail-closed SNBT parsing.

## Web start and resume

`POST /api/cannons/:name/start` accepts the displayed `assignment` and blueprint `version`. It requires browser-admin authentication, CSRF and same-origin checks, an existing confirmed binding and a ready automatic Schematic job. A per-station lock serializes it with preparation and transfers. The signed host `start` action verifies the exact file/hash, owner, target, options, range and live printer state before changing native execution state. Initialization is read back before continuing. Resume preserves the same verified cached plan and counters. It does not replace inventory or reset a printer. Only an explicit user start/resume action starts construction; selecting a plan, saving options and automatic preparation do not.

Status inspection can read a bounded set of relevant fields when the full native block response is oversized. It must retain identity and state consistency checks and reject incomplete data. Live status is pushed through SSE, while feeder leases retain their existing expiry rules.
