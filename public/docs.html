API-Dokumentation

OpenAPI

Zugang

Token in der App unter Agent-Zugang erzeugen und als Authorization: Bearer atc_… mitschicken. Ein Token handelt im Namen seines Accounts, jede Änderung landet mit Namen im Protokoll. „Nur lesen“-Tokens dürfen ausschließlich GET-Anfragen.

Begriffe

Live / Bestand
Snapshot der echten ATM10-Welt im Campus-Ausschnitt (x −64…223, y 48…319, z −96…223). Wird automatisch alle paar Minuten aus den Region-Files gelesen, wenn der Server gespeichert hat.
Edition
Die jeweils aktuelle Version aller nicht archivierten Baupläne, also das, was gebaut werden soll.
Bauplan
Vanilla-/Create-Structure-NBT plus origin (Weltkoordinate der Ecke mit den kleinsten x/y/z). minecraft:air = abreißen, minecraft:structure_void = nicht anfassen.
Planungsstand
Der Snapshot, auf dem eine Version geplant wurde (baseSnapshotId). Daraus ergibt sich „seit Planung geändert“.

Status und Konflikte

Konflikt
Eine Block-Entity (Maschine, Kiste, AE2 …) steht dort, wo der Bauplan etwas anderes setzt oder abreißt, oder zwei Baupläne beanspruchen dieselbe Zelle mit unterschiedlichen Blöcken.
Geändert
Im Baufeld hat sich der Bestand seit dem Planungsstand verändert. Jemand hat dort gebaut.
Offen
Keine Konflikte, noch nicht fertig gebaut.
Gebaut
Live entspricht dem Bauplan zu ≥ 99,9 %.
409 Bearbeitungskonflikt
Beim Hochladen baseVersion mitschicken. Hat inzwischen jemand eine neuere Version hochgeladen, antwortet die API mit 409 samt currentVersion. Dann neu herunterladen, Änderungen zusammenführen, erneut hochladen.

Baupläne blockgenau ändern (empfohlen für Agents)

Statt NBT-Dateien zu bauen, schickt ein Agent Operationen. Der Server wendet sie auf die aktuelle Version an, prüft Blocknamen, rechnet die Analyse gegen den Live-Bestand und speichert eine neue Version. Mit "dryRun": true gibt es nur die Vorschau (keine Schreibrechte nötig).

H="Authorization: Bearer $CAMPUS_TOKEN"

# Ansehen: als Text-Schichten (Weltkoordinaten), als JSON oder den echten Bestand
curl -s -H "$H" "$CAMPUS_URL/api/blueprints/40_Pavillon/layers?y=63..66"
curl -s -H "$H" "$CAMPUS_URL/api/blueprints/40_Pavillon/blocks?coords=world"
curl -s -H "$H" "$CAMPUS_URL/api/world/blocks?from=38,63,8&to=50,70,20&format=layers"

# Vorschau: was würde sich ändern, was steht im Weg?
curl -s -X POST -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/blueprints/40_Pavillon/edits -d '{
  "dryRun": true, "coords": "local",
  "edits": [
    {"op": "fill", "from": [0,0,0], "to": [8,0,8], "block": "minecraft:polished_andesite"},
    {"op": "fill", "from": [0,1,0], "to": [8,4,8], "block": "minecraft:stone_bricks", "mode": "hollow"},
    {"op": "set",  "pos": [4,1,0], "block": "minecraft:oak_door", "properties": {"facing": "south", "half": "lower"}},
    {"op": "replace", "match": "minecraft:*_planks", "block": "minecraft:spruce_planks"},
    {"op": "clear", "from": [3,5,3], "to": [5,5,5]}
  ]}'

# Speichern: gleiche Anfrage ohne dryRun, mit baseVersion (409 = jemand war schneller)
curl -s -X POST -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/blueprints/40_Pavillon/edits \
  -d '{"baseVersion": 3, "note": "Tür + Dach", "edits": [ … ]}'

# Neuer Bauplan aus Operationen
curl -s -X POST -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/blueprints/new \
  -d '{"fileName":"41_Kiosk.nbt","origin":[60,63,20],"size":[5,4,5],"name":"41 · Kiosk","edits":[{"op":"fill","from":[0,0,0],"to":[4,3,4],"block":"minecraft:oak_planks","mode":"hollow"}]}'
set / setMany
Einzelne Blöcke: {"op":"set","pos":[x,y,z],"block":"ns:name","properties":{…}}
fill
Quader from–to. mode: all (Standard), hollow (Hülle, innen Luft), outline (nur Hülle), keep (nur leere Zellen), replace (nur Zellen, die match entsprechen).
replace
Alle Blöcke, die match (Glob mit *) entsprechen, durch block ersetzen; optional nur in from–to, mit keepProperties bleiben Ausrichtungen erhalten.
clear / void
clear setzt Luft (= im Spiel abreißen), void entfernt Zellen aus dem Plan (= Bestand nicht anfassen).
copy
Bereich from–to nach dest kopieren (z. B. Fensterachsen wiederholen).
coords / grow
"coords":"world" für Weltkoordinaten statt relativ zur Bauplan-Ecke. "grow":true vergrößert den Bauplan, wenn Operationen darüber hinausgehen.
Antwort
changes (gesetzt / abgerissen / freigegeben), warnings (z. B. Blockname weder in der Welt noch in einem Bauplan bekannt – Tippfehler?), neue origin/size, analysis gegen Live inkl. Maschinen im Weg, ohne dryRun die neue version.

Materialliste und Rest-NBT

Die Materialliste vergleicht die Baupläne mit dem Live-Bestand und zählt, was noch fehlt – als Items (Wandfackel → Fackel, Türen und Betten einmal, doppelte Stufen zweimal, Wasser → Eimer, Create-Bänder → Bandverbinder + Wellen, ummantelte Wellen → Welle + Gehäuse). Zellen, die mehrere ausgewählte Baupläne gemeinsam haben, zählen einmal. Die Rest-NBT enthält nur Blöcke, die noch fehlen, hat aber dieselbe Größe und denselben origin wie der volle Bauplan: an derselben Stelle platzieren, und die Schematicannon setzt im normalen Modus nur noch den Rest. Entities (Rahmen, Rüstungsständer) sind nicht enthalten, damit sie nicht doppelt gesetzt werden.

H="Authorization: Bearer $CAMPUS_TOKEN"

# Was fehlt für einen Bauplan? (json | text | csv | html mit Blockbildern)
curl -s -H "$H" "$CAMPUS_URL/api/blueprints/01_Technikhof_P01/materials?format=text"

# … für mehrere oder alle Baupläne (ohne ids = ganzer Campus)
curl -s -H "$H" "$CAMPUS_URL/api/materials?ids=01_Technikhof_P01,02_Produktionshalle_P02&format=text"

# Rest-NBT: nur fehlende Blöcke; Maschinen-Zellen werden standardmäßig ausgelassen
curl -s -H "$H" -o 01_rest.nbt "$CAMPUS_URL/api/blueprints/01_Technikhof_P01/remaining.nbt"
curl -s -H "$H" -o rest.zip "$CAMPUS_URL/api/remaining.zip"   # alle Baupläne, manifest.json mit Statistik
clear
Luft-Zellen (Abriss) übernehmen. Standard: nein. Nur für den Vanilla-Strukturblock sinnvoll: Die Schematicannon ignoriert Luft im normalen Modus, und im Modus „Replace Solid with Empty“ räumt sie alle nicht enthaltenen Zellen leer – also auch schon Gebautes.
skipBlocked
Zellen auslassen, in denen eine Block-Entity (Maschine, Kiste …) steht. Standard: ja, damit nichts versehentlich zerstört wird.
skipChanged
Zellen auslassen, die sich seit dem Planungsstand verändert haben. Standard: nein.

Liegt ein ME-Bestand vor (siehe unten), steht bei jedem Item zusätzlich me (im ME-System), short (fehlt auch dort) und craftable; mit ?me=0 abschaltbar.

Schematicannons am ME-System (CC:Tweaked)

Ein CC:Tweaked-Computer mit Advanced-Peripherals-ME-Bridge füllt die Kiste an einer Schematicannon mit genau den Items, die ihr Bauplan noch braucht, unterste Schichten zuerst und nur ein paar Stacks auf Vorrat. Fehlt etwas im ME, kann er es craften lassen. Wechselt der Auftrag oder ist der Bau fertig, gehen Reste zurück ins ME. Welche Kanone welchen Bauplan baut, wird in der App unter „Kanonen“ festgelegt.

# am Computer im Spiel (Token mit Scope „Station“ unter /app → Agent-Zugang anlegen)
wget run https://campus.logge.top/cc/install.lua
  • Aufbau: ME Bridge und Kiste (einfache Kiste oder Fass) beide direkt am Computer oder beide am selben Wired-Modem-Netz; die Kiste berührt die Kanone. Alternativ set campus.direction up = Richtung von der Bridge zur Kiste.
  • In der Kanone „Skip Missing“ ausschalten, Modus „Replace Solid with Any“ lassen. Dann wartet sie auf fehlende Blöcke und baut weiter, sobald nachgefüllt ist.
  • Läuft mit Advanced Peripherals 0.8.x (ATM10 ab 8.1) und 0.7.x; bei 0.7.x zusätzlich set campus.direction <north|…|up|down> setzen, weil 0.7 Seitennamen von der Bridge aus auflöst. Wasser, Lava und Kessel-Füllungen setzt die Kanone nicht; Eimer werden deshalb nicht geliefert.
  • Der Fortschritt hängt am Live-Bestand und ist so frisch wie der letzte Weltspeicher (einige Minuten). Damit eine leere Kiste das ME nicht leerzieht, liefert der Computer je Auftrag höchstens etwa 110 % der Menge.
H="Authorization: Bearer $CAMPUS_TOKEN"

# Kanonen mit Auftrag, Fortschritt und letztem Status des Computers
curl -s -H "$H" $CAMPUS_URL/api/cannons

# Bauplan zuweisen (pinnt die aktuelle Version) und Optionen setzen – braucht einen Schreib-Token
curl -s -X PUT -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/cannons/nord-1 \
  -d '{"blueprint":"01_Technikhof_P01","options":{"bufferStacks":2,"autoCraft":true}}'

# Was der Computer abholt: Items unterste Schicht zuerst, Optionen, Auftragsnummer
curl -s -H "$H" $CAMPUS_URL/api/cannons/nord-1/plan

# ME-Bestand (zuletzt gemeldet) und welche Items der Campus noch braucht
curl -s -H "$H" "$CAMPUS_URL/api/me/stock?items=1"
curl -s -H "$H" $CAMPUS_URL/api/me/wanted
bufferStacks
So viele Stacks je Item höchstens in der Kiste (1–16, Standard 2).
gunpowder
Schießpulver, das immer in der Kiste liegen soll (0–64, Standard 16).
autoCraft · craftBatch
Fehlt ein Item im ME und gibt es ein Muster, einen Crafting-Auftrag über höchstens craftBatch Stück starten (Standard aus, 256).
returnLeftovers
Reste nach Auftragswechsel oder Fertigstellung zurück ins ME (Standard an).
skipBlocked
Zellen mit Maschine im Weg nicht beliefern, wie in der Rest-NBT (Standard an).
paused
Computer liefert nichts.

Ganze NBT-Dateien und Snapshots

H="Authorization: Bearer $CAMPUS_TOKEN"

# 1. Überblick: Live-Snapshot, Fortschritt, Konflikte je Bauplan, Überlappungen
curl -s -H "$H" $CAMPUS_URL/api/status

# 2. Details eines Bauplans inkl. Versionen und Analyse (Beispielkoordinaten)
curl -s -H "$H" $CAMPUS_URL/api/blueprints/01_Technikhof_P01

# 3. Herunterladen (aktuelle oder ?version=N)
curl -s -H "$H" -o 01_Technikhof_P01.nbt $CAMPUS_URL/api/blueprints/01_Technikhof_P01/download

# 4. Neue Version hochladen (roh)
curl -s -X PUT -H "$H" -H "content-type: application/octet-stream" --data-binary @01_Technikhof_P01.nbt \
  "$CAMPUS_URL/api/blueprints/01_Technikhof_P01/nbt?baseVersion=3&note=Dach+angepasst"

# 4b. … oder als JSON (auch für neue Baupläne, dann origin Pflicht)
curl -s -X POST -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/blueprints \
  -d '{"fileName":"40_Pavillon.nbt","origin":[40,63,10],"name":"40 · Pavillon","nbtBase64":"…","note":"Entwurf"}'

# 5. Position verschieben (erzeugt neue Version)
curl -s -X PATCH -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/blueprints/40_Pavillon \
  -d '{"origin":[42,63,10],"baseVersion":1}'

# 6. Bestand sofort neu erfassen (statt auf den nächsten Lauf zu warten)
curl -s -X POST -H "$H" -H "content-type: application/json" $CAMPUS_URL/api/snapshots -d '{"force":true}'

# Alles als ZIP (für den Create-Ordner schematics/)
curl -s -H "$H" -o campus.zip $CAMPUS_URL/api/blueprints.zip

Die heruntergeladenen .nbt-Dateien kommen im Client in .minecraft/schematics/ und lassen sich dann am Schematic-Table hochladen und mit der Schematicannon bauen.
